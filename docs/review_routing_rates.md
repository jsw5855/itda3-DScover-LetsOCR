## 3. 분기 정의 (위에서부터 먼저 해당하는 하나)

| 분기 | 조건 | 직원 행동 |
|---|---|---|
| MANUAL | 최종 `final_date`에 `NONE`이 있음 (부분 NONE 포함) | 수동 입력 |
| CHOOSE | 최종 단계에서 `find_all_candidates`의 서로 다른 날짜가 2개 이상 (M) | 후보 중 선택 |
| RECHECK | 선택 후보의 q < 0.90, 또는 q를 정할 수 없음 | 재확인 |
| CONFIRM | 위에 해당하지 않음 | 확인 후 승인 |

- q: 선택된 날짜가 나온 박스(글자와 중심 좌표가 같은 박스)들의 인식 신뢰도 최솟값
- q와 M은 제출 코드 `ocr_pipeline.stage_result`로 계산한다. `scripts/diagnose_correct_controls_50.py`의 `evidence()`와 같은 정의다.
- 기준값 0.90은 이 데이터를 보고 조정하지 않았다.
- **오류 방향**: 날짜가 틀렸을 때 예측이 정답보다 늦으면 `late`, 이르면 `early`, 어느 한쪽에 NONE이 있으면 `not_comparable`로 둔다.
- **오류 크기**: 두 날짜가 모두 완전할 때 `예측 - 정답`의 일수(`days_off`, 양수 = 늦음)다.

## 4. 입력과 방법

### 4.1 cascade

- **production (대표값)**: 체크아웃한 코드의 `ocr_pipeline.run_cascade`를 쓴다. 지금은 Policy B다.
  - 1단계에 후보가 있고 q < 0.90 또는 M이면 highres를 한 번 더 읽고, q가 더 높은 쪽을 쓴다.
  - 1단계에 후보가 없으면 rotation → highres → CLAHE 순서로 넘어간다.
- **first_candidate (비교용)**: 후보가 처음 나온 단계에서 멈춘다. Policy B 이전 방식이다.

## 6. ROI 계산에 쓰는 법 (틀만 제공, 시간 값은 서현이 정함)

상품 N개를 처리할 때 직원 작업 시간은 다음과 같다.

```text
직원 시간 = N x ( 0.167 x T_수동입력 + 0.126 x T_후보선택 + 0.073 x T_재확인 + 0.635 x T_승인 )
기존 방식 = N x T_수동입력              # 모든 상품을 눈으로 보고 입력한다고 가정할 때
절감률    = 1 - 직원 시간 / 기존 방식
위험      = N x 0.011  (지난 상품이 확인 없이 통과할 수 있는 건수, 95% CI 0.6–2.2%)
```

- T 값은 매장 실측이나 가정으로 채운다. 이 문서의 비율은 T 값과 무관하다.
- 위험 건수는 미검수 라벨 기준이다. C절의 권장대로 라벨을 확인하면 더 정확해진다.

## 7. 한계

- **개발 데이터 포함**: 701장에는 Parser와 cascade 개발에 쓴 사진이 섞여 있다. 독립 검증 수치가 아니며, 새 데이터에서는 비율이 더 나쁠 수 있다.
- **미검수 라벨**: B·C는 대부분(632장) 한 팀 라벨만 있는 미검수 후보값 기준이다. 확정 정확도로 쓰면 안 된다. A(분기 비율)는 라벨이 필요 없다.
- **코드 의존**: 현재 제출 코드 기준이다. OCR, Parser, cascade가 바뀌면 다시 계산해야 한다(`docs/review_routing_rates_RERUN.md`).
- **대표값의 출처**: 대표값은 저장된 파싱 결과로 계산했다. 최종 수치는 701장 × 4단계 원본 OCR을 최종 코드로 다시 파싱해서 만든다(`--full-stage-raw`).
- **도메인 차이**: 식품 포장 사진 기준이다. 화장품(작은 인쇄, 곡면 용기, 영문 표기)이나 매장 현장 촬영 사진과는 비율이 다를 수 있다.
- **신뢰구간의 범위**: 표본 크기에서 오는 오차만 반영한다.
- **오류 원인 해석**: 틀린 정도 표 아래의 원인(숫자 오인식, 제조일 선택, 연도 순서)은 날짜 차이 패턴으로 추정한 것이다. 이미지로 확인하지 않았다.
