## 2. 전체 파이프라인과 Parser의 위치

```
사진 → [OCR: ocr_pipeline.predict_image]
          4단계 cascade: original_512 → rotation_270 → highres_1024 → clahe
          각 단계 OCR 결과 = [{text, confidence, bbox}, ...]
       → [Parser: date_parser.parse_expiration_date]  ← 이번에 바뀐 부분
       → {year, month, day, final_date}   (읽을 수 없는 칸은 "NONE", 전부 NONE이면 final_date="NONE")
```

- **cascade와 Parser는 연결되어 있습니다.** 각 단계에서 `has_candidate(detections)` = `select_final_date(...) is not None`이면 그 단계에서 멈춥니다.
  - Parser가 **후보를 더 많이 찾으면** 1단계에서 더 자주 멈춥니다. 빨라지지만, 1단계 OCR이 틀렸을 때 뒤 단계로 기회가 안 넘어갈 수 있습니다.
  - Parser가 **후보를 더 엄격하게 거르면** 다음 단계로 넘어가는 사진이 늘어 느려집니다.
- 그래서 Parser 변경은 **정확도와 "다음 단계로 넘어가는 사진 수"를 같이 봐야** 합니다.

## 3. date_parser 구조 (변경 후)

| 파일 | 역할 | 이번 변경 |
|---|---|---|
| `types.py` | `TextBox`, `DateResult` | 없음 |
| `extract.py` | 글자에서 날짜 모양 토큰 추출 (정규식, 구체적인 패턴부터 순서대로) | 패턴 추가, 전처리 `split_glued()`, 일 뒤 잡음 제거, `accept` 콜백, 월/2자리연도·연도 없는 월.일 추출 함수 |
| `interpret.py` | 토큰 → (연, 월, 일) 해석 후보 + 점수 (달력 검증, 순서 우선순위) | 형식 안내가 있을 때 쓰는 순서 표 `_DMY_HINT_ORDER_PRIOR`, `order_hint` 인자 |
| `hints.py` | **새 파일**. 사진 속 형식 안내 문구 감지 | `detect_format_hint()` → `"dmy"` / `"month_year"` / `None` |
| `keywords.py` | 앵커(소비기한 등)·제외(제조일자 등) 키워드, 위치 거리 | 제외 키워드에 `산란일자`, `산란일` 추가 |
| `select.py` | 모든 박스에서 후보를 모아 최종 1개 선택 | 형식 안내 적용, 실패 매칭 자리 양보, 연도 없는 월.일 대체 후보, 옆 박스 연도 합치기 |
| `crossref.py`, `parser.py` | 제조일 대비 검증, 진입점 | 없음 |

**처리 순서** (`select.find_all_candidates`)
1. 사진 전체 글자에서 형식 안내를 감지합니다(`hints.detect_format_hint`).
2. 박스마다 `extract_date_tokens(text, accept=...)`로 토큰을 뽑습니다.
   - 먼저 `split_glued`로 텍스트를 정리합니다: `C`→0 보정, 끊긴 연도 붙이기, 붙은 날짜·시각 사이에 공백 넣기.
   - `accept`는 달력상 해석이 하나도 없는 토큰을 거절해서, 그 자리를 다른 패턴에 넘깁니다.
3. 형식 안내가 `month_year`이면 `MM.YY` 토큰도 추가로 찾습니다.
4. **사진 전체에서 후보가 하나도 없을 때만** 연도 없는 월.일(`MM.DD`) 후보를 찾습니다. 바로 옆에 4자리 연도만 있는 박스가 있으면 합칩니다.
5. 이후 선택 로직(앵커·제외 키워드 거리, 소비기한 우선, 늦은 날짜 우선)은 **예선과 동일**합니다.

## 4. 바뀐 규칙 상세 (적용 순서대로, 단계마다 701장 재채점)

## 5. 시도했다가 버린 규칙 (측정 결과 손해 — 다시 시도하지 말 것)

| 시도 | 701장 측정 | 이유 |
|---|---|---|
| 2자리 연도 날짜를 항상 일.월.년 우선 | **+7 / −42** | 한국 제품의 `26.04.24`(연.월.일)가 대부분이라 크게 손해. 구분 기호, 한글 유무, EXP 키워드로도 두 그룹이 갈리지 않음 |
| 4자리 연도 날짜를 월/일 우선 | **+4 / −28** | 일/월이 훨씬 많음 |
| 구분 기호가 섞인 짧은 숫자(`4.24-5`)를 코드로 보고 제외 | **+2 / −7** | OCR이 실제 날짜의 구분 기호도 섞어 읽음(`26.07-14`) |
| 연도 없는 월.일에 콜론(`07:24`) 허용 | 위험 3장 확인 | 시각과 구분 불가 |

## 6. 결과

| 구분 | 예선 최종본 | 개선 후 |
|---|---|---|
| 전체 701장 | 538 (76.75%) | **579 (82.60%)** |
| 기존 300장 | 247 (82.33%) | 263 (87.67%) |
| 신규 401장 | 291 (72.57%) | 316 (78.80%) |
| 검수 확정 69장 | 38 (55.07%) | 53 (76.81%) |
| 고정 표본 250장 (seed 42) | 199 (79.60%) | 212 (84.80%) |
| 새로 틀린 사진 | | 0장 |
| 다음 단계로 넘어가는 사진 | 153 | 124 |

- **실제 실행 확인**: 결과가 바뀌는 53장(새로 맞힘 41 + 단계만 바뀜 12)을 이수민 PC에서 예선 `predict_image` + 새 `date_parser`로 돌렸습니다. **53/53이 재채점 예상과 날짜·멈춘 단계까지 일치**했고, 1단계로 끝난 사진은 평균 11.5초로 예선과 같은 속도였습니다.
- **주의(과대평가 가능성)**: 개선 대상을 이 701장 오답에서 골랐기 때문에 +41은 새 데이터에서는 더 작을 수 있습니다. 다만 규칙은 사진 번호가 아니라 글자 형식 기준이고, 매 단계 새로 틀린 사진이 0장이었습니다.
- **라벨 주의**: 정답 701장 중 69장만 검수 확정입니다. 나머지 632장 중 606장은 한 팀 라벨만 있어 교차 확인되지 않았습니다. 이번에 라벨 오류 6장(127, 1142, 3223, 851, 1870, 1336)을 이미지로 확인해 고쳤고, 위 수치는 고친 라벨 기준입니다.

## 7. AI 작업 시 지켜야 할 규칙 (이 문서를 AI에 넣을 때 같이 전달)

1. **main은 수정하지 않습니다.** 작업은 claude 브랜치(또는 별도 브랜치)에서만 합니다.
2. **2자리 연도의 기본 순서는 연.월.일로 유지합니다.** 일.월.년은 형식 안내 문구가 있을 때만 씁니다(5번 표 참고, +7/−42).
3. **4자리 연도의 월/일 기본 순서(일/월 > 월/일)를 바꾸지 않습니다** (+4/−28).
4. **연도 없는 월.일은 "사진에 다른 후보가 전혀 없을 때만", "점 구분만", "단위 제외"** 조건을 유지합니다. 조건을 풀면 1단계에서 일찍 멈추는 사진이 생깁니다.
5. **새 규칙은 반드시 701장 재채점으로 "새로 맞힌 사진 / 새로 틀린 사진"을 모두 확인한 뒤** 넣습니다. 새로 틀린 사진이 있으면 원인을 보고 규칙을 좁히거나 버립니다.
6. Parser를 바꾸면 cascade 멈춤 위치도 바뀝니다. **"다음 단계로 넘어가는 사진 수"(속도)를 같이 기록**합니다.
7. 개선 대상은 **글자 형식 기준**으로 만들고, 특정 사진 번호에 맞춘 예외 규칙은 만들지 않습니다.

## 8. 검증 방법 (OCR 재실행 없이 몇 초)

```bash
# 저장된 701장 OCR 원문으로 현재 date_parser를 재채점 (예선 cascade 그대로 재현)
python scripts/replay_parser.py docs/run701/ocr_dump.jsonl docs/parser_review/labels_701.csv \
    --baseline docs/parser_review/replay/after_T7.csv
# 출력: 정답 수, "unknown"(저장 안 된 단계가 필요한 사진), 다음 단계로 넘어간 사진 수,
#       기준 대비 GAINED / LOST 사진 목록
```

- `replay_parser.py`는 수정 전 코드로 돌리면 실제 701장 실행과 **701/701 동일**합니다(검증 완료).
- 기준 파일: `docs/parser_review/replay/baseline_main.csv`(예선, 538), `after_T7.csv`(최종, 579). 단계별 중간 결과도 같은 폴더에 있습니다.
- `unknown`: Parser 변경 때문에 cascade가 원래 멈춘 단계보다 뒤로 가야 하는데, 그 단계 OCR이 저장돼 있지 않은 사진입니다. 0이 아니면 해당 사진만 실제로 다시 돌려야 합니다.
- 단위 테스트: `pytest tests/test_date_parser` → **134개 통과**. 전체 `pytest`는 169개 중 164개 통과이고, 실패 5개는 로컬 `data/`·`labels/labels_300.csv`가 필요한 평가 테스트로 main에서도 같은 이유로 실패합니다.
  - 새 테스트: `tests/test_date_parser/test_final_round_cases.py`(실제 OCR 원문 사례 44개), `test_hints.py`(3개)
