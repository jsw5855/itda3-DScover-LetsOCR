## 2. 파이프라인과 cascade (AI 참고용 배경)

- 검출 `PP-OCRv6_medium_det`, 인식 `korean_PP-OCRv5_mobile_rec`, CPU 전용
- 주요 설정: `text_det_box_thresh=0.7`, `text_det_limit_type="max"`, recognition batch 6, MKLDNN 켬
- `ocr_pipeline.predict_image`의 4단계 cascade

| 단계 | 입력 | 이 PC 평균 시간 |
|---|---|---|
| `original_512` | 긴 변 512px | 약 10초 |
| `rotation_270` | 512px를 270° 회전 | 약 10초 |
| `highres_1024` | 긴 변 1024px | 약 40초 |
| `clahe` | 512px + CLAHE 대비 보정 | 약 10초 |

  - 선우님 PC 기준으로는 단계당 약 1~2.4초입니다(예선 기록).
- **멈춤 규칙**: 각 단계에서 Parser가 날짜 후보를 하나라도 찾으면(`has_candidate`) 그 단계에서 멈춥니다. 네 단계 모두 없으면 첫 단계 결과를 씁니다(`original_no_candidate`).
  - 후보가 **틀린 날짜여도 멈춥니다.** 제출 시간 제한(Run All 2400초) 때문에 생긴 구조입니다.
- **Parser가 바뀌면 멈추는 단계도 바뀝니다.** 새 Parser로 다음 단계까지 가는 사진이 153 → 124장으로 줄었습니다. **OCR·cascade 실험은 새 Parser 기준으로 해야** 결과가 맞습니다.

## 3. 분류 기준

- **OCR 문제**: 저장된 모든 단계의 OCR 원문 어디에도 정답 날짜가 온전하게 없는 경우입니다. 못 찾았거나, 잘못 읽었거나, 일부만 읽은 경우입니다.
- **Parser 문제(제외)**: 원문에 정답이 온전히 있는데 Parser가 해석하지 못한 경우입니다. Parser 담당이 처리합니다.
- 사진마다 저장된 모든 단계의 원문을 사람이 확인해서 유형을 정했습니다.

## 6. 실험·검증 방법

- **저장된 OCR 원문**: claude 브랜치 `docs/run701/ocr_dump.jsonl`
  - 한 줄이 사진 한 장입니다: `{image_id, file, method, prediction, stages:[{stage, seconds, has_candidate, prediction, detections:[{text, confidence, bbox}]}]}`
  - 실행된 단계만 들어 있습니다.
- **OCR을 바꾼 뒤 평가**: 바뀐 OCR로 같은 형식의 dump를 만들면 `scripts/replay_parser.py`로 새 Parser 기준 정답 수와 **새로 맞힌 사진 / 새로 틀린 사진**을 바로 셀 수 있습니다.
  ```bash
  python scripts/replay_parser.py <새 ocr_dump.jsonl> docs/parser_review/labels_701.csv \
      --baseline docs/parser_review/replay/after_T7.csv
  ```
  - 기준점: 579/701 (새 Parser + 예선 OCR)
- **부분 실험**: 701장 전체는 이 PC로 수 시간이 걸립니다. 먼저 **4번 항목의 해당 유형 사진 목록과, 비슷한 수의 현재 정답 사진**을 같이 돌려 손해가 없는지 보고, 최종 후보만 전체로 확인하는 것을 권합니다(팀 실험 정책).
- **시간**: 제출 조건 Run All 2400초 제한입니다. 단계 추가나 해상도를 올리면 **전체 시간을 선우님 환경에서 꼭 확인**해야 합니다.

## 7. AI 작업 시 지켜야 할 규칙 (이 문서를 AI에 넣을 때 같이 전달)

1. **main은 수정하지 않습니다.** 별도 브랜치에서 작업합니다.
2. **평가는 새 Parser(claude 브랜치 `date_parser`) 기준으로** 합니다. 예선 Parser로 재면 cascade 멈춤 위치가 달라서 결과가 맞지 않습니다.
3. OCR·cascade 변경은 **새로 맞힌 사진과 새로 틀린 사진을 모두 확인**하고, **전체 실행 시간(2400초 제한)**을 같이 기록합니다.
4. 정답 99장 중 **89장은 미검수 라벨**입니다. OCR 원문과 정답이 크게 다르면 먼저 이미지를 확인합니다(이번에 라벨 오류 6장을 이렇게 찾음).
5. 특정 사진 번호에 맞춘 예외 처리는 하지 않습니다.
6. Parser 규칙 변경이 필요해 보이면 Parser 담당과 먼저 공유합니다. Parser 변경은 cascade 멈춤에 영향을 줍니다.

## 8. CSV 칸 설명 (`ocr_issues_v6.csv`)

| 칸 | 내용 |
|---|---|
| `image_id`, `file_name` | 대회 이미지 번호와 파일명 (`상품사진입니다` 폴더) |
| `type` | D1~D6 |

| `prediction`, `cascade_result_stage` | 새 Parser 기준 현재 예측과 멈춘 단계 |
| `stages_run` | 실행된 단계 수 (1~4) |
| `ocr_original_512` ~ `ocr_clahe` | 각 단계 OCR 원문 중 **날짜와 관련 있어 보이는 줄만** (숫자 패턴, 영문 월, EXP·BEST·까지·기한). 실행 안 된 단계는 그렇게 표시. 전체 원문은 `ocr_dump.jsonl` |
| `label_source` | 정답 출처. `approved`는 검수 확정, `candidate`는 미검수. `existing_300`은 우리 팀, `incoming_432`는 다른 팀 |
| `labeler_note` | 예선 때 라벨 작성자 메모 (기존 300장만, 24장에 있음) |
